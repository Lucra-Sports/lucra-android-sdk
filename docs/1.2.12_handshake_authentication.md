# Handshake Authentication

Handshake auth signs a user into Lucra using **your** existing session, with no Lucra login UI. Instead of asking a user who is already signed into your app to verify a phone number again, your app hands Lucra a short-lived, partner-signed token; Lucra exchanges it for a Lucra session behind the scenes.

It is purely additive. Phone auth still exists and remains the fallback: if no provider is registered, or the exchange fails, the SDK presents the phone auth screen exactly as it does today. The one exception is `TosNotAccepted` — a new user who has not accepted the Terms of Service is resolved by the `HandshakeTOS` flow (or an allowed `bypassTosAgreement` request), not by phone auth. See [Terms of Service](#terms-of-service).

> Handshake auth requires Lucra-side provisioning (a shared signing key and a token exchange profile for your tenant). Contact Lucra before integrating.

## How it works

1. You register a **token provider** — a suspending lambda that returns a partner-signed JWT identifying your current user.
2. Lucra calls that provider (with a 5s timeout) and exchanges the token for a Lucra session.
3. The user lands in the same Lucra account they would have reached via phone auth, matched on the phone number in the token.

Your session never leaves your app: the provider hits **your** backend with **your** credentials, and Lucra only ever sees the token it returns.

## The token contract

Your backend signs the token with the shared key Lucra issues you. The key must never ship in the app — the provider exists so the app can fetch an already-signed token from your authenticated API.

* **Algorithm:** `HS256`
* **Payload:**

```json
{
  "sub": "your-stable-user-id",
  "phone_number": "+15555550100",
  "email": "user@example.com",
  "iat": 1735689600,
  "jti": "b9d1f0e6-2f0b-4a3e-9b06-8a9e5b0f3f4c"
}
```

| Claim | Required | Notes |
|---|---|---|
| `sub` | Yes | Your stable identifier for the user. |
| `phone_number` | Yes | E.164. This is what Lucra resolves the account by — a match signs into the existing Lucra user, a new number creates one. |
| `email` | No | Populates the Lucra profile when present. |
| `iat` | Yes | Issued-at, in seconds. Tokens are accepted for 60s (30s clock tolerance), so mint per request rather than caching. |
| `jti` | Yes | Unique per token; the handle for replay protection. |

Send nothing else — no `iss`, `aud`, or `exp`. An unexpected claim can only reject a token that would otherwise pass.

## Step 1 — Register the provider

Register once, any time after `LucraClient.initialize`. Registering only stores the lambda: it signs nobody in, has no auth side effects, and is safe to call repeatedly from composition or lifecycle callbacks.

```kotlin
LucraClient().registerHandshakeAuthTokenProvider {
    // Runs on a background dispatcher. Use YOUR session against YOUR backend.
    myApi.fetchLucraHandshakeToken()
}

// Pass null to clear it — Lucra flows go back to phone auth.
LucraClient().registerHandshakeAuthTokenProvider(null)
```

The lambda must return within **5 seconds** or the attempt fails with `ProviderTimedOut`.

## Step 2 — Sign in

Registering does not sign anyone in; you choose the moment.

```kotlin
LucraClient().signInWithHandshakeAuth { result ->
    when (result) {
        is SignInWithHandshakeAuthResult.Success -> {
            val user = result.sdkUser
            Log.d("Lucra", "Signed in as ${user.username}")
        }
        is SignInWithHandshakeAuthResult.Failure -> {
            // Do not dead-end the user — phone auth still works.
            Log.w("Lucra", "${result.error.message} — ${result.error.recoverySuggestion}")
        }
    }
}
```

Call it at launch to have the user authenticated before any Lucra UI could appear, or later if you would rather not pay for the exchange until Lucra content is actually reached. `Success` is reported once the user **profile** has loaded, not merely once the tokens land, so the returned `SDKUser` is immediately usable. Concurrent calls share a single in-flight exchange.

### An existing session wins

Calling this while a user is already signed in reports that user and runs no exchange. The same holds while their stored session is still being restored — the usual state a launch-time call arrives in — so it is safe to call unconditionally on every app start without racing the restore or minting a redundant session.

A returning user therefore keeps the session they already had, tokens and all. To sign a **different** user in, sign the current one out first and call this once that completes:

```kotlin
LucraClient().logout(context)
LucraClient().signInWithHandshakeAuth { result -> /* … */ }
```

Signing in as a different user without logging out first is not supported: the call will simply report the user who is already signed in.

### Or let the SDK do it

If you only register a provider, the SDK signs the user in on its own wherever it would otherwise have shown the login screen:

* **Presenting an auth-gated Lucra flow** while signed out runs the handshake first, holding a loading state instead of the phone auth screen.
* **Tapping auth-gated content mid-flow** (for example joining a tournament) runs the handshake behind a blocking loading overlay, then completes the action the user tapped. System Back cancels the wait.
* **A failed token refresh** re-authenticates silently rather than dropping the user back to a login screen.
* **Tapping a signed-out [Lucra component](1.2.8_lucracomponents.md)** — the floating action button, the mini public feed, runs the handshake in place instead of presenting Lucra's login inside your screen.

Every one of these falls back to phone auth if the handshake declines or fails — with one exception, covered in [Terms of Service](#terms-of-service) below.

Components sit in your own view hierarchy, so the SDK shows no loading UI of its own for that last one — covering your screen is your call, not ours. Observe `isHandshakeAuthInFlight` (below) if you want a spinner while the exchange runs. The tap itself is not carried through the sign-in: the component re-renders signed in, and the user acts from there.

## Terms of Service

A user who is **new to Lucra** has no account yet, and Lucra will not create one until they
agree to its Terms of Service. Their first exchange is therefore refused with
`HandshakeAuthError.TosNotAccepted`. Users who already have a Lucra account are never
affected.

This is the one failure that is **not** a cue to fall back to phone auth — phone auth cannot
create the account either. Treating it as a generic failure dead-ends exactly the users you
are trying to onboard.

On the wire, the exchange carries `tos_accepted` only once the user has agreed, and the refusal
before that comes back as `TOS_NOT_ACCEPTED`, which is what `HandshakeAuthError.TosNotAccepted`
maps. Neither value is yours to send: the SDK attaches the agreement and resubmits. They are named
here because they are what you will see in a token-exchange log.

**When Lucra is presenting the flow**, there is nothing to do: the terms step is shown inline,
and once the user agrees the sign-in resumes and continues into the flow they asked for.

**When you called `signInWithHandshakeAuth` yourself**, present `LucraFlow.HandshakeTOS` off
that specific error. It needs no session, captures the agreement, resubmits the sign-in with a
fresh token from your provider, and dismisses once the user is signed in.

```kotlin
LucraClient().signInWithHandshakeAuth { result ->
    when (result) {
        is SignInWithHandshakeAuthResult.Success -> proceed(result.sdkUser)
        is SignInWithHandshakeAuthResult.Failure -> when (result.error) {
            // New user, one agreement short of an account.
            is HandshakeAuthError.TosNotAccepted ->
                LucraClient().getLucraDialogFragment(LucraFlow.HandshakeTOS)
                    .show(supportFragmentManager, LucraFlow.HandshakeTOS.toString())
            // Everything else: phone auth still works.
            else -> presentPhoneAuth()
        }
    }
}
```

Present `HandshakeTOS` **only** in response to that error. It is not an entry point.

### Skipping the step

If your own onboarding already captures agreement to Lucra's terms, the step can be skipped:

```kotlin
LucraClient().registerHandshakeAuthTokenProvider(bypassTosAgreement = true) {
    myApi.fetchLucraHandshakeToken()
}
```

The bypass is honored only for tenants Lucra has permitted. Otherwise the request is ignored,
new users see the terms step exactly as they would have, and a log records that it was asked
for and not granted — so a build that silently loses the bypass behaves correctly rather than
failing. **Talk to Lucra before setting it**; it carries a legal obligation you are taking on.

## Observing state

```kotlin
// True while an exchange is running. Lucra suppresses its own login UI during it;
// observe it if you want to show your own loading state.
LucraClient().isHandshakeAuthInFlight
    .onEach { inFlight -> /* … */ }
    .launchIn(scope)

// Why the last attempt failed, or null. Because failures fall back to phone auth
// silently, this is how you tell a working fallback from a broken integration.
LucraClient().handshakeAuthError
    .onEach { error -> error?.let { Log.w("Lucra", "${it.message} — ${it.recoverySuggestion}") } }
    .launchIn(scope)
```

## Sign-out

`LucraClient().logout(context)` ends the Lucra session and stops the SDK from silently re-authenticating the user on a token refresh. It does **not** unregister your provider: the next time you present a Lucra flow that needs a session, the SDK will run the handshake again and sign the same user back in — which is usually what you want, since they are still signed into your app.

To keep a user signed out of Lucra, clear the provider as part of your own sign-out:

```kotlin
LucraClient().registerHandshakeAuthTokenProvider(null)
LucraClient().logout(context)
```

## Timeouts

| Wait | Limit | On expiry |
|---|---|---|
| A stored session still being restored | 5s | Proceeds with the exchange |
| Your token provider | 5s | `HandshakeAuthError.ProviderTimedOut` |
| SDK initialization (tenant resolution) | 15s | `HandshakeAuthError.TenantIdUnavailable` |
| A gated sign-in the user is waiting on | 10s | Falls back to phone auth |
| The user profile after a successful exchange | — | `HandshakeAuthError.ProfileTimedOut` |

## Error reference

Every failure carries a `message` and a `recoverySuggestion` naming what to go look at.

| Error | Meaning | What to check |
|---|---|---|
| `HandshakeAuthError.NoProviderRegistered` | `signInWithHandshakeAuth` was called with no provider | Call `registerHandshakeAuthTokenProvider` before presenting a Lucra flow |
| `HandshakeAuthError.ProviderTimedOut` | Your lambda did not return within 5s | Your token endpoint's reachability from the device. On an emulator, `localhost` is the emulator — use `10.0.2.2` for the host machine |
| `HandshakeAuthError.ProviderFailed(cause)` | Your lambda threw | `cause`; typically your own session is expired or the endpoint errored |
| `HandshakeAuthError.ExchangeFailed(cause)` | Lucra rejected the token | Signature (is the key the one Lucra issued, and encoded the same way?), `iat` freshness, and the payload shape above. The message carries the underlying error code and description |
| `HandshakeAuthError.TosNotAccepted` | The user is new to Lucra and has not accepted the Terms of Service; the exchange refused with `TOS_NOT_ACCEPTED` | Nothing — this is not a fault. Present `LucraFlow.HandshakeTOS`, not phone auth. See [Terms of Service](#terms-of-service) |
| `HandshakeAuthError.TenantIdUnavailable` | SDK initialization never produced a tenant | That `LucraClient.initialize` completed with a valid API key |
| `HandshakeAuthError.ProfileTimedOut` | The session landed but the profile did not | Connectivity; retry the sign-in — the credentials are already installed |
| `HandshakeAuthError.Unknown` | A concurrent sign-out superseded the attempt, or the sign-in failed unexpectedly | Retry the sign-in if it is still wanted |

## API reference

| Member | Type |
|---|---|
| `registerHandshakeAuthTokenProvider(provider: (suspend () -> String)?)` | `Unit` |
| `registerHandshakeAuthTokenProvider(bypassTosAgreement: Boolean, provider: (suspend () -> String)?)` | `Unit` |
| `signInWithHandshakeAuth(onResult: (SignInWithHandshakeAuthResult) -> Unit)` | `Unit` |
| `isHandshakeAuthInFlight` | `StateFlow<Boolean>` |
| `handshakeAuthError` | `Flow<HandshakeAuthError?>` |

```kotlin
sealed interface SignInWithHandshakeAuthResult {
    data class Success(val sdkUser: SDKUser) : SignInWithHandshakeAuthResult
    data class Failure(val error: HandshakeAuthError) : SignInWithHandshakeAuthResult
}

sealed interface HandshakeAuthError {
    val message: String
    val recoverySuggestion: String
}
```
